How should a workflow file and a project override look and read?

The v2 engine walks a ticket through steps written in a data file. Below are the real files: the global workflow that reproduces v1's pipeline, this repository's override, a Drupal site's override, and one custom step kind in TypeScript. Then a model you can press buttons on, so the loop and the budgets can be felt rather than read.

Three things to react to: is the fix loop readable? Are the patch operations obvious? What is missing? Answer at the bottom, or click any line to annotate it.

The shape, in one picture

The list is the order. A step that finds a problem names a repair edge: run fix, then run me again, spending one slot of a named budget each time. Budgets live at the top of the file and never refill. Dashed boxes run only when their when: holds; the dotted box runs only through a repair edge.

The files

Real text, not sketches. The two overrides are shown next to the change they make to the global workflow, so a patch op can be judged by what it does.

~/.config/orchestration/workflow.yaml · one per machine · reproduces v1's pipeline

What to look at

  • Budgets first. bounces: 3 and ci_repairs: 2 are v1's numbers. A repair edge must name one, or the loader refuses the file.
  • The loop is one line on the step that detects the problem: findings: { repair: fix, budget: bounces }. Read it as "run fix, then run me again".
  • fix sits in the list but carries trigger: repair. It never runs in the plain walk. Three different steps can repair through the one fix step.
  • Skip lanes are when: on tests and review. Nothing else changes for a trivial or no-code ticket.
  • "Merges wait for a human" is when: settings.merge == auto plus else: { block: ... }. Is that readable, or does it want its own step?
  • Gates are names (tests-green, ci-green-on-head). They are code in the engine; the file only says which one applies.
  • runner appears only on agent steps. mr, ci and merge are built-in kinds that imply how they run.

<repo>/.orchestration/workflow.yaml · committed in this repository

Effective workflow: identical to the global one. Tests-only verification and the exact-SHA CI gate are already how the global workflow behaves, so this file patches nothing.

What to look at

  • Almost empty. extends: global, one setting, patch: []. Most projects will look like this.
  • Question: should a project with nothing to change commit a file at all, or does "no file" mean "global as is"?
  • settings are the knobs the global workflow already reads in its when: conditions. Patch ops change the list; settings change how the existing list behaves.

<repo>/.orchestration/workflow.yaml · committed in a Drupal site's repository

What to look at

  • Three ops, each addressed by a step id: insert_after: review, insert_before: verify, insert_after: verify. Ops apply in order, so the second one can name the step the first one made.
  • verify shares bounces with review, as in v1. a11y shares it too. Three senders, one budget of three. Tight? (The Drupal walkthrough below ends at 3/3.)
  • uses: points at the TypeScript module that registers a11y-scan. Forget it and the loader says so (see "What the loader rejects").
  • merge: human is a setting, not a patch. The global merge step reads it.
  • Not shown here: drop, replace, set (merge fields; null deletes), move (before/after) and from: scratch. Same addressing, same loud failures.

<repo>/.orchestration/steps/a11y-scan.step.ts · the escape hatch

What to look at

  • Registered by name, like Pi Durable extensions. The file says kind: a11y-scan; the engine resolves kinds when it loads the file, not per run.
  • A kind declares its outcomes. The first one falls through. Every other outcome must be mapped under on:, or the ticket blocks when it happens. Nothing fails open.
  • Question for the step-kind ticket: built-in agent steps all share kind agent with outcomes pass / findings / failed. Is one kind right, or should review be its own kind with its own outcomes?

    Your reactions

    Pick, then press Queue answer. Nothing is sent until you press Send to Agent in the Lavish bar. The first option in each pair is my recommendation.

    1. Is the fix loop readable?

    One line on the detecting step, a named budget, and a fix step marked trigger: repair.

    2. Are the patch operations obvious?

    insert_after: review plus a step:, addressed by id, applied in order, whole file rejected on any bad id.

    3. Where does verify live?

    Shown: the global has no verify; the Drupal site inserts it. v1 carried verify globally and preflight decided whether it ran.

    4. How does merge wait for a human?

    Shown: when: settings.merge == auto with else: { block: awaiting human merge }. The ticket ends blocked; a person merges by hand.

    5. What is missing?

    Things I already know the file does not say: model routing per step, the review findings ledger, how the lane is chosen, a human granting one extra repair, a loop whose body is longer than one step. Anything else?
