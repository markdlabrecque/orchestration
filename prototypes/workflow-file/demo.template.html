How should a workflow file and a project override look and read?

The v2 engine walks a ticket through steps written in a data file. Below are the real files: the global workflow that reproduces v1's pipeline, this repository's override, a Drupal site's override, and one custom step kind in TypeScript. Then a model you can press buttons on, so the loop and the budgets can be felt rather than read.

The shape, in one picture

The list is the order. A step that finds a problem names a repair and a budget: run the repair, spend one slot, then run me again. Repairs are declared once at the top of the file; they are not in the list. Dashed boxes run only when their when: holds. A spent budget blocks the ticket for a human.

~/.config/orchestration/workflow.yaml · one per machine · reproduces v1's pipeline

What to look at

  • Budgets, then repairs, then settings, then steps. Everything a step refers to by name is declared above it.
  • repairs.fix is declared once. review, verify and ci all name it. It never appears in the ordered list, so the list reads as the plain walk.
  • The loop is still one line on the step that detects the problem: findings: { repair: fix, budget: bounces }. Read it as "run fix, then run me again".
  • verify is behind a setting. Its when: is a list: standard lane and verification is not local-tests. This repo switches it off with one setting; the Drupal site switches it on.
  • merge-approval is a human step. It runs only when settings.merge == human, and the engine waits for a person to say go.
  • Gates are names (tests-green, ci-green-on-head). They are code in the engine; the file only says which one applies.
  • runner appears only on agent steps. mr, ci, merge and human are built-in kinds that imply how they run.

<repo>/.orchestration/workflow.yaml · committed in this repository

Effective workflow: the global list, unchanged. verify and merge-approval are skipped at run time because of the two settings. Nothing is patched.

What to look at

  • Settings only. Two lines say how this repo verifies and merges. Most projects will look like this.
  • Settings vs patch: settings change how the existing list behaves; patch ops change the list. A project needs a patch only to add or remove a step.
  • Question: should a project whose settings equal the defaults commit a file at all?

<repo>/.orchestration/workflow.yaml · committed in a Drupal site's repository

What to look at

  • Two settings switch on verify and the merge approval. No patch op needed for either.
  • Three ops, each addressed by a step id: insert_after: spec (a second human gate), insert_before: verify (start DDEV), insert_after: verify (the a11y scan). Ops apply in order.
  • a11y repairs through the same fix and spends the same bounces as review and verify. Three senders, one budget of three. The Drupal walkthrough below ends at 3/3.
  • uses: points at the TypeScript module that registers a11y-scan. Forget it and the loader says so (see "What the loader rejects").
  • Not shown: drop, replace, set (merge fields; null deletes), move (before/after) and from: scratch. Same addressing, same loud failures. One set appears in the rejects below.

<repo>/.orchestration/steps/a11y-scan.step.ts · the escape hatch

What to look at

  • Registered by name, like Pi Durable extensions. The file says kind: a11y-scan; the engine resolves kinds when it loads the file, not per run.
  • A kind declares its outcomes. The first one falls through. Every other outcome must be mapped under on:, or the ticket blocks when it happens. Nothing fails open.
  • Question for the step-kind ticket: built-in agent steps all share kind agent with outcomes pass / findings / failed. Is one kind right, or should review be its own kind with its own outcomes?

    What the loader rejects

    Most tools let a project change a shared config by merging a second file on top. Misspell a name there and nothing complains: the tool quietly adds a new entry with the wrong name and ignores what you meant. This file format does the opposite.
