# Ticket 113 report: Deterministic selftest interrupt tests

Issue: https://github.com/markdlabrecque/orchestration/issues/113

## Result

The three interrupt tests no longer depend on how the test runner was started or on machine load. They were failing deterministically whenever the suite ran in a backgrounded shell, which is how concurrent suite runs from other sessions usually start.

Root cause, three parts:

1. A backgrounded shell starts the runner with SIGINT set to SIG_IGN. Python keeps SIG_IGN instead of installing its default interrupt handler, and the runner passed that to `orch`. The fake's SIGINT was ignored, so no KeyboardInterrupt fired and all three tests failed. Repro: `sh -c 'python3 -m unittest <3 tests> > log 2>&1 & wait'` gave 3 failures; run in the foreground, the same 3 pass.
2. The fakes signalled `os.getppid()` blindly. If `orch` was already gone, the fake signalled whatever its parent had become. `orch` also shared the runner's process group, so nothing isolated the interrupt to the test's own child.
3. The orca and herdr fakes slept a fixed 5 seconds after the SIGINT and then carried on, and the engine fake carried on immediately. Under load the interrupt could land after the fake had finished its work.

Fix (test file only, `tests/test_orch_adapters.py`; `scripts/orch` unchanged):

- `orch_isolated()` starts `orch` for the three interrupt tests only, with `start_new_session=True` and SIGINT reset to SIG_DFL in the child, so Python installs its default interrupt handler. Other tests start `orch` unchanged.
- The fakes use `interrupt_parent()`. It signals only a parent that is its own session and group leader and is not pid 1, which is the isolated `orch`. Otherwise it writes an error and exits non-zero without signalling anything. It never uses killpg.
- After the interrupt, the fakes wait until `orch` kills them, bounded by a 60 second deadline, instead of sleeping a fixed time. `orch`'s `subprocess.run` and `run_engine` kill the child on KeyboardInterrupt, so the wait ends.
